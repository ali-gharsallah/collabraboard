# Lot L1 — Signal fiable · notes

## P-L1-1 — Runner CPSI : le faux-vert, cause racine et correctif

### Cause racine
`services/cpsi-server-py/run_tests.py` exécutait chaque test dans un `try/except` qui **capturait
toute exception**, l'imprimait comme `FAIL` et l'agrégeait dans un compteur — puis le script se
terminait **sans jamais appeler `sys.exit`**. Le processus rendait donc **toujours le code 0**, même
avec des tests rouges. Tout consommateur qui juge la santé de la suite par le **code de sortie**
(shell `set -e`, `&&`, orchestrateur) voyait « vert » quel que soit l'état réel.

En CI, cela était masqué par une garde de chaîne : `grep -q "### 20/20 suites vertes ###"`. Fragile
par nature — elle dépend d'un marqueur imprimé, pas du verdict du processus ; un consommateur hors CI
(ou une reformulation du grep) réintroduit le faux-vert silencieusement. C'est le constat de
`docs/audit/TEST_AUDIT.md` (« run_tests.py exits 0 even on failure; CI relies solely on a grep guard »).

### Correctif
1. **Propagation du code de sortie** — `run_tests.py` agrège désormais le nombre total de tests
   échoués et termine par `sys.exit(0 if total_ko == 0 else 1)`. Casser un assert dans n'importe quel
   bloc fait sortir le runner avec un code ≠ 0 (vérifié : injection dans `test_cpsi_bloc1.py` →
   `19/20`, exit 1).
2. **Canari de méta-vérification** — `services/cpsi-server-py/canary.py` contient un test
   **délibérément rouge**, HORS de la suite normale (nom sans préfixe `test_` ni suffixe `_test` →
   ni `run_tests.py` normal, ni un vrai `pytest` ne le collecte). `run_tests.py --canary` l'exécute
   et **doit** rendre un code ≠ 0. Ce canari garde la propagation elle-même contre toute régression :
   si `--canary` rendait 0 un jour, la propagation serait cassée.
3. **CI** — étape `5c` : `run_tests.py | tee` (le code de sortie du runner traverse le `pipefail`,
   la garde grep reste en second rideau). Nouvelle étape `5c-bis` : `run_tests.py --canary` **doit**
   échouer, sinon la CI est rouge (faux-vert de retour).

|---|---|---|
| `run_tests.py` | exit 0 · `20/20` | exit 0 · `20/20` |

Critère de sortie P-L1-1 atteint : casser volontairement un assert dans `test_cpsi_bloc1.py` fait
échouer la commande de CI ; le canari est vert en mode normal (non exécuté) et rouge sur demande.

## P-L1-2 — Bloc 61 (Analytique 2G) en CI bloquante + contrat Nest↔Python

### Conflit tranché (canon vs playbook) — arbitré avec le porteur
Le playbook demandait de rendre **bloc 61 (Analytique 2G, R399–R403) bloquant en CI**. Or
`backend-tests/aml-gap/bloc61.analytique-2g.spec.ts` est un test **Nest** qui importe
`evaluateScenario` de `src/aml/engine` avec la mention `// à implémenter` (« TESTS ROUGES AVANT
CODE ») : il attend une logique 2G **côté Nest** qui n'existe pas — et **ne doit pas** exister, car
la **décision 4** (canon, cf. commentaire CI + `bridge.py` : « Analytique 2G — jamais en Nest ») place
ces détecteurs statistiques **uniquement** dans le moteur CPSI Python (`olive_cpsi/analytique_2g.py`,
`DETECTEURS_2G`). Rendre bloc 61-Nest vert imposerait de **réécrire le moteur en Nest** — interdit.

**Décision (ratifiée) : « Bloquer 2G côté Python ».** On honore la décision 4 :
- **2G est désormais réellement bloqué là où il vit** : le **CPSI bloc 20** (« Analytique 2G AML gap »,
  `tests/test_cpsi_bloc20.py`) tourne déjà en CI à l'étape `5c`, et depuis **P-L1-1** cette étape
  **propage le code de sortie** — un test 2G rouge y échoue désormais la CI (plus de faux-vert).
- **bloc 61-Nest reste EXCLU** (`--testPathIgnorePatterns bloc61`), non pas silencieusement mais par
  **diagnostic assumé** : c'est un test « rouge avant code » d'une logique que le canon interdit en Nest.
  Le rendre bloquant reviendrait à demander une réécriture proscrite. À supprimer / re-cibler si un jour
  la décision 4 est révisée (auquel cas : mettre à jour l'ADR + le commentaire CI + `CLAUDE.md` d'abord).

### Contrat Nest↔Python (frontière vérifiée de façon bloquante)
La porte NestJS se fie à la **forme** de la réponse du pont `bridge.py` (protocole d'enveloppe R248).
On fige ce contrat :
- **Schéma committé** : `docs/contracts/cpsi.schema.json` — toute réponse est SOIT `{resultat, meta}`
  SOIT `{erreur_typee}` (jamais les deux, jamais aucune), `contract_version` toujours présent
  (`oneOf` + `additionalProperties:false`).
- **Banc** : `services/cpsi-server-py/contract.test.mjs` invoque le **vrai** pont en sous-processus pour
  **3 payloads représentatifs** (signal simple → `score` ; franchissement de bande → `score` ; config
  tenant versionnée → `rules`) **+ une enveloppe d'erreur typée** (contrat non supporté), et valide
  chaque réponse RÉELLE contre le schéma. Gate autonome (convention du repo pour les vérifs qui
  traversent Node↔Python : cf. `services/screening/*.test.mjs`, `services/*-py/run_tests.py`) — aucun
  Postgres, aucun bootstrap Jest ; **CI étape `5d`, bloquante**.
